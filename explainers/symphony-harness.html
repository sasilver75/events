Boundary rule: the orchestrator is the control process around the agent. It applies policy, creates isolated work, and records evidence; it does not decide how to implement the issue.

Core idea

The harness is a long-running issue reader and isolated agent launcher.

It does not replace Linear, GitHub, Codex, or the repo. It coordinates them: Linear chooses work, GitHub receives code, Codex does the task, and the orchestrator enforces the execution envelope.

Tracker

Linear is the control plane

Issues become runnable only when they match the repo policy: active state, AFK label, no HITL label, blockers done, and inside the Spur project.

Scheduler

Go orchestrator owns scheduling

It polls Linear, claims eligible issues, starts bounded workers, retries or continues turns, and cancels work that stops being eligible.

Workspace

Tart creates one macOS VM per issue

The workspace is a per-issue macOS VM clone, not a directory or Docker container. This is what makes iOS work possible.

Runner

Codex app-server runs the agent turn

Codex receives the rendered issue prompt, talks through the app-server protocol, and can use host-proxied tools such as Linear GraphQL.

Boundary: the orchestrator schedules, isolates, and records. The agent still owns normal issue comments, PR creation, and Linear closeout because those are part of the work contract in WORKFLOW.md.

Why this exists

Spur needs a coding-agent service that runs inside an iOS-capable macOS environment.

The harness must support Xcode, the iOS Simulator, codesign, Supabase, Docker/Colima, Go, GitHub PRs, and Linear handoff. A Linux-only sandbox cannot provide that environment.

The failure mode without a harness
  • Agents pick arbitrary work or skip tracker policy.
  • Tooling state leaks between tasks.
  • Credentials are copied ad hoc.
  • Finished code may never get a PR or Linear closeout.
  • Long-running attempts do not leave consistent status or artifact records.

System boundaries

The harness separates policy, control, execution, agent work, and evidence.

Each boundary has a different owner and failure mode. Keeping them separate makes it easier to diagnose whether a problem came from tracker policy, VM execution, agent behavior, or evidence collection.

Policy plane

WORKFLOW.md

Defines eligibility states, hooks, runtime limits, credentials mode, and the per-issue instructions.

Control plane

Linear + scheduler

Linear stores work. The Go orchestrator polls, filters, claims, retries, cancels, and escalates.

Execution plane

Tart VM + hooks

Each issue gets an isolated macOS environment with repo checkout, Xcode, Simulator, Go, and artifacts.

Agent plane

Codex app-server

Codex receives a rendered prompt, works inside the VM, calls dynamic tools, and emits protocol telemetry.

Evidence plane

PR, comments, logs, JSON

GitHub PRs, Linear pickup/closeout comments, copied logs, status snapshots, and canary artifacts are the audit trail.

Debugging rule

When something fails, first identify the plane that failed. A label mismatch points to tracker policy, a missing PR points to agent handoff, and a missing status file points to evidence collection.

policy control execution agent evidence

WORKFLOW.md

The workflow file is the contract between repo policy and runtime execution.

It is deliberately versioned in the repo so the agent's operating instructions, eligibility rules, and hooks change with code review rather than invisible local configuration.

tracker:
  kind: linear
  active_states:
    - Ready
    - In Progress

workspace:
  base_image: spur-base
  root: ~/.tart/vms

agent:
  runner: claudecode
  max_concurrent_agents: 2
  max_turns: 20
  max_unproductive_successes: 3

credentials:
  linear_access: vm_env

codex:
  command: codex app-server stdio
What it controls
tracker

Which Linear project and states are considered active.

workspace

Which Tart base image is cloned for each issue.

hooks

What host-side shell runs after create, before run, after run, and before remove.

agent

Which runner is selected, concurrency limits, turn limits, retry behavior, and stuck-loop threshold.

prompt

The rendered task instructions that tell Codex how to pick up work, implement, verify, open a PR, and close out Linear.

Dynamic reload

Workflow reload lets policy change without restarting the daemon.

The orchestrator checks the file modification time on poll ticks. New prompt text, hooks, limits, active states, and timeouts apply to future runs.

Reload scope

If a prompt, hook command, active state, timeout, or limit changes, future runs can pick it up while the service keeps running.

Restart-only change

Switching between claudecode and codex requires restart or canary because the runner object is built at startup.

Operational response

Operators can tighten policy after a run exposes a gap, such as missing handoff comments, without stopping active work.

Linear eligibility

Not every issue is runnable. The scheduler applies Spur policy before Codex sees anything.

Eligibility rationale
  • Ready means the issue has enough spec to attempt.
  • AFK means it is explicitly permitted for unattended agent work.
  • No HITL means the issue does not require a human conversation first.
  • Blockers Done prevents work from racing ahead of dependencies.
  • Same gate for daemon and --once prevents canary runs from bypassing policy.

Workspace model

Tart provides the macOS guest required for iOS build and simulator work.

Docker is appropriate for Linux services. Tart runs macOS guests, so the agent has access to Xcode, Simulator, Keychain, codesign, and other Apple tooling.

Tart VM

  • Full macOS virtual machine on Apple Silicon.
  • Can run Xcode, iOS Simulator, Keychain, codesign, and native Apple tooling.
  • Higher startup and resource cost than Docker; required when a task needs macOS APIs or Apple tooling.
  • Per-issue clone is named like spur-ticket-SAM-54.

Docker container

  • Lightweight Linux process isolation.
  • Great for Go services, Postgres clients, and many backend tasks.
  • Cannot run Xcode or iOS Simulator inside Linux.
  • On macOS, Docker itself runs Linux inside a hidden VM.

Lifecycle hooks

Hooks are host-side shell scripts that prepare and clean the VM.

They are declared in WORKFLOW.md, but run on the host with VM metadata in environment variables.

after_create

First clone setup

Runs once for a new VM. Configures Git, clones the repo, checks out main, and pulls the latest code.

before_run

Every attempt setup

Copies issue JSON, credentials boundary files, Codex or Claude identity snapshots, and refreshes Git remote auth.

after_run

Attempt artifact copy

Copies Claude project logs, Codex logs, and issue snapshots out to the run log directory.

before_remove

Final artifact copy

Runs before terminal VM deletion and copies build artifacts or final evidence back to the host.

Runner interface

The orchestrator talks to runners through one shared contract.

Claude and Codex are concrete implementations. The worker does not need to know every protocol detail; it needs a start/resume result, events, telemetry, and final status.

Concrete runners
codex

Starts codex app-server over SSH, initializes JSON-RPC, starts or resumes a thread, starts a turn, handles dynamic tool requests, and captures telemetry.

claudecode

Streams Claude Code headless output over SSH and now fits the same result/event model. Useful as legacy fallback, but not where future investment should go if Codex is the production direction.

Why this matters: the scheduler can stay stable while the concrete agent runtime changes. That is what made adding Codex possible without rewriting the orchestrator loop.

Codex app-server runner

The Codex runner uses the app-server protocol instead of a one-shot shell command.

What gets captured

Session ID, thread ID, turn ID, completion or error event, token usage, and rate-limit snapshots.

What gets advertised

Dynamic tools are sent on both thread start and resume so continuation turns keep host-side capabilities.

What gets rejected

Unsupported app-server requests are rejected rather than silently hanging; approval requests are answered with a cancel decision.

Credential boundary

Codex supports keeping the Linear token on the host.

vm_env injects Linear access into the VM. host_proxy keeps Linear access on the host and exposes only a scoped GraphQL tool to the agent.

vm_env

Token enters the VM

  • Hook writes LINEAR_API_KEY for agent use.
  • Works for simple CLI/API calls.
  • Token exposure includes the guest environment.
  • Still the literal default in the merged WORKFLOW.md until you flip production.
host_proxy

Token stays on the host

  • Worker omits LINEAR_API_KEY from Codex environment.
  • Hook receives empty SPUR_LINEAR_TOKEN.
  • Codex receives linear_graphql dynamic tool.
  • Supported only for agent.runner: codex.

One worker run

A worker is one claimed issue moving through one agent attempt.

Success path

Agent opens PR, comments on Linear, moves issue to In Review. Orchestrator records success and releases the worker.

Continuation path

If work remains active and allowed turns remain, the next run can resume the prior session or reuse the same VM state.

Terminal path

If Linear reaches Done, Canceled, or Duplicate, the VM is cleaned up.

Linear state machine

The harness is driven by issue state, not by a hidden job queue.

Linear is the source of truth for whether work may start, keep running, needs review, is done, or requires a human decision.

Ready

Eligible only if AFK is present, HITL absent, blockers Done, and issue is in the Spur project.

In Progress

The agent has picked it up. The issue remains active while the VM and worker are alive.

In Review

The agent opened a PR and posted closeout. Human or CI review happens here.

Done

Terminal. The orchestrator runs final artifact collection and removes the VM.

Needs Human

Side exit. Used when the agent needs a decision or the loop guard detects unproductive success.

Active states

Ready and In Progress are pollable states in WORKFLOW.md.

Review state

In Review is intentionally not active, so the orchestrator does not keep dispatching after PR handoff.

Terminal states

Done, Canceled, and Duplicate trigger cleanup.

Agent-owned handoff

The agent is responsible for implementation, PR handoff, and tracker closeout.

The workflow prompt treats a code change without a PR, Linear comments, and a state transition as operationally incomplete.

Required before exit
  • Post pickup comment on the Linear issue.
  • Move issue to In Progress while work is active.
  • Create a branch and PR against main.
  • Post closeout comment with PR link, acceptance-criteria table, drift list, artifacts, and verification.
  • Move issue to In Review after the PR opens.
Why the orchestrator does not do it all

The scheduler does not inspect the implementation deeply enough to judge whether the ticket is satisfied. The agent has the diff, test output, and task context needed to explain the result. The orchestrator only handles bounded stuck-loop escalation.

agent writes handoff comments agent opens PR orchestrator records status orchestrator handles loop escalation

Definition of complete: code merged is not the only target. The issue needs an auditable path from Linear, to VM work, to PR, to verification, to Linear state.

Stuck-loop guard

A clean runner exit does not guarantee that the issue moved forward.

The failure case is an agent turn that exits successfully while Linear remains active. Without a guard, the orchestrator would continue the issue until max_turns.

Productive success

Runner exits, PR exists, closeout exists, issue is now In Review or terminal.

Unproductive success

Runner exits cleanly, but issue remains Ready or In Progress.

Escalation threshold

After agent.max_unproductive_successes, the orchestrator stops continuing the issue and moves it to Needs Human.

Resumability

Sessions, threads, and turns are how a long task becomes inspectable.

The Codex app-server path gives the harness stable identifiers for the overall session, the app-server thread, and the specific turn that produced a result.

session_id

Run handle

The resumable handle the orchestrator records for an agent attempt. It is what lets continuation relate to prior agent context.

thread_id

Codex conversation

The app-server thread that owns messages and dynamic tool availability. Tools are advertised on start and resume.

turn_id

Specific attempt

The concrete unit that completed, failed, timed out, or emitted usage/rate-limit telemetry.

Verification detail: when a canary succeeds, the status snapshot names the exact Codex session, thread, and turn that produced the result.

End-to-end run

From Linear issue to merged code, the system crosses seven boundaries.

Forward path
  1. Human writes/triages a Linear issue and marks it Ready + AFK.
  2. Orchestrator polls Linear and filters candidates.
  3. Worker claims the issue and ensures a Tart VM exists.
  4. Hooks clone/update the repo and stage credentials according to mode.
  5. Codex receives the rendered WORKFLOW.md prompt and performs the task.
  6. Agent pushes branch, opens PR, posts closeout, moves Linear to In Review.
  7. Orchestrator records status, tokens, rate limits, session IDs, and artifacts.
Feedback path
  1. Each tick refreshes tracker state for running issues.
  2. If the issue becomes terminal, cleanup runs and VM is deleted.
  3. If the issue leaves active states, worker is canceled and claim is released.
  4. If successful turns leave the issue active repeatedly, it escalates to Needs Human.
  5. If the operator changes WORKFLOW.md, future runs reload supported policy changes.
  6. If a canary is running, the status file can be verified without live credentials.
  7. If GitHub CI fails, the PR/checks become the next debugging surface.

Failure handling

The harness records failures as bounded, inspectable states.

Unattended runs can fail because of tracker changes, VM setup, hooks, timeouts, unsupported tool calls, or missing handoff. The harness should make each case visible and recoverable.

VM or hook failure

Worker records an error, the run can retry according to backoff, and logs/artifacts identify which hook failed.

Agent timeout or stall

Runner returns a timeout/stall error, worker integrates the failure, and the orchestrator decides retry or stop by configured limits.

Issue changed underneath

Reconciliation notices terminal or inactive state and cancels active workers rather than continuing stale work.

Unsupported Codex request

The app-server client explicitly rejects unsupported requests so the turn does not hang silently.

Unproductive success

Repeated clean exits with active Linear state move to Needs Human and stop additional continuation turns.

Missing status snapshot

In one-shot mode, requested --status-file write failure fails the run instead of becoming a hidden warning.

Production posture

The Codex path is verified, but WORKFLOW.md still controls the production default.

The merged workflow still keeps Claude as the literal default, while the canary verified the Codex runner and host-proxy path. Moving production to Codex requires changing the workflow defaults.

What changes

Daemon dispatch starts Codex by default and keeps Linear on the host.

What stays

What to keep briefly

The Claude runner can remain as a fallback implementation until you are comfortable deleting legacy code.

Recap

Summary of system ownership

Linear decides what is eligible

Ready/In Progress, AFK, no HITL, blockers Done, Spur project.

The orchestrator decides how it runs

Claims, VM lifecycle, hooks, runner selection, retries, cancellation, reload, status.

Codex decides how to solve the issue

Implements, verifies, opens PR, comments on Linear, and moves issue state according to the workflow prompt.

The repo owns policy, the orchestrator owns isolation and scheduling, and the agent owns implementation and handoff.
